# Quickmd v3 需求对齐清单

> 状态：待决策（2026-10-22）
> 背景：负责人决定参考 Scroll Reverser 对 Quickmd 做三个方向的改造——**开机自启、架构优化、极轻极简**。本文档用于对齐需求：先拆解参考对象，再列出现状，最后把待决策问题摊开，每条附背景解释与建议。决策结果记录在第 5 节。

---

## 1. 参考对象拆解：Scroll Reverser 做对了什么

实测对象：`/Applications/Scroll Reverser.app`（v2.0.2，pilotmoon 出品，开源）。

| 特征 | 事实 | 对 Quickmd 的意义 |
|---|---|---|
| 应用形态 | `LSUIElement=true`，纯菜单栏，无 Dock 图标 | Quickmd 已是 `.accessory`，形态一致，无需改 |
| 体积 | 可执行文件 500KB | 可对标；Quickmd 主二进制约几 MB（Swift 运行时底座），差距在 WebContent 子进程 |
| 开机自启 | 二进制内含 `LoginItemController` 类管理登录项 | 借鉴其模式，但用现代 API 实现（见 Q1） |
| 依赖 | 仅内置 Sparkle（自动更新框架） | **不借鉴**：我们连自动更新也不要，保持零依赖 |
| 「重」的部分 | 29 种语言本地化、AppleScript 脚本支持、独立偏好窗口 | **不借鉴**：这些是「完整」不是「轻」 |
| 产品心智 | 单用途：一个图标、一个开关、用完即走 | 借鉴：Quickmd 的全部交互就是「碰刘海 → 打字 → Esc」 |

**一句话**：借鉴 Scroll Reverser 的「纯菜单栏 + 登录项 + 单用途」哲学，不借鉴它的本地化/脚本/更新体系。

## 2. 现状盘点

**已完成（v2.1）**：刘海 30Hz 触发（零权限）、面板预览/激活两态、分块 WYSIWYG 编辑器（标题/加粗/斜体/删除线/行内代码/链接/裸 URL/列表/嵌套/任务清单/引用/代码块/分隔线）、前缀即变形、Enter/Backspace/Tab 编辑行为、全套快捷键 + 13 键工具栏、400ms 防抖自动保存、打开文件（菜单 + 拖拽）、状态栏、深浅色适配、XSS 防护、55 项 Node 单测、4 个诊断开关。内存日常约 37MB（主进程 20MB + WebContent 17MB）。

**已知问题 7 项**（详见 `MAP.md` 问题清单）：插入链接失效（P0）、insertLink XSS 绕过、代码块按钮撞车、拖拽高亮死代码、光标恢复与文档不符、打开文件后面板不回归、无 git（已修）。

## 3. 待决策问题

### Q1 开机自启：用什么机制，默认开还是默认关？

**背景**：macOS 实现开机自启有三条路：

| 方案 | 做法 | 评价 |
|---|---|---|
| 系统设置手动加 | 用户自己去「设置 → 通用 → 登录项」拖入 | app 零代码，但体验差、不可控 |
| SMAppService（推荐） | `SMAppService.mainApp.register()`，macOS 13+ 官方 API | 现代标准做法；app 内一行代码注册/注销；系统设置里可见可管；无需 helper 进程 |
| SMLoginItemSetEnabled + helper | 老方案，需单独的 helper target | 重（多一个二进制），Scroll Reverser 属这类旧模式 |

**待定**：默认状态。开机自启不弹任何窗口，打扰为零，但「默认注册」意味着用户没同意就常驻了。
**建议**：SMAppService + 菜单栏菜单加「开机自启」勾选项（状态存 UserDefaults）+ **默认开启**（本次改造的目标就是自启，且零打扰；随时可关）。

### Q2 「极简」砍到什么程度？（本清单最重要的一题）

**背景**：编辑器和「开关类」应用不同，不能砍到只有一个开关。可分三档：

| 方案 | 内容 | 代价 |
|---|---|---|
| A 保守 | 只砍已坏的插入链接；工具栏瘦身；其余全保留 | 改动小，但「极简」度低，内存/体积不变 |
| **B 均衡（建议）** | 砍整个工具栏（快捷键 + markdown 前缀语法已覆盖全部功能，README 补一张速查表）；砍拖拽打开（保留菜单 ⌘O）；状态栏只留保存态圆点 + 字数；菜单精简为 4 项（打开文件/开机自启/立即保存/退出）；砍首次演示便签；块类型全保留 | 交互面减半，代码可删约 150 行；编辑器核心价值不变 |
| C 激进 | 连状态栏、快捷键都砍，只剩编辑区 + Esc；甚至去掉 WKWebView 换 NSTextView | 内存可从 37MB 降到约 10MB，但等于重写编辑器，所见即所得体验大幅降级，**不推荐** |

**建议选 B**。若选 C 的「去 WebView」需三思：37MB 里 17MB 是 WebContent 进程，这是「网页版编辑器」路线的固有成本，换来的是极低的编辑器开发量。

### Q3 「优化架构」具体指什么？

| 方案 | 内容 | 评价 |
|---|---|---|
| **A 修复 + 拆分（建议）** | 修掉 7 项已知问题；`main.swift`（594 行单文件）按职责拆成多文件（AppDelegate / NotchPanel / EditorWebView / TriggerController / MenuController / Store）；`editor.js` 按「纯函数内核 / DOM 序列化 / UI 事件」三层拆模块（Node 单测保持只依赖内核层，不受影响）；补 DOM 交互层的自动化测试思路 | 保持 WKWebView 架构不变，纯代码组织优化，风险低 |
| B 只修 bug | 架构不动，只修问题清单 | 最小改动，但「优化」落空 |
| C 换原生编辑器 | NSTextView 重写 | 等于推翻架构重来，不推荐 |

**建议选 A**。「优化架构」在保持技术栈不变的前提下的具体动作：拆分 + 修复 + 每层有测试。

### Q4 公开仓库的定位：自用备份，还是可分发？

这决定要不要做签名和发布流程：

| 定位 | 需要做的事 |
|---|---|
| 自用备份 / 作品展示（现状即够） | 无 |
| 可分发（别人下载能用） | ad-hoc 签名 + README 写 Gatekeeper 绕过说明；或 $99/年开发者账号做完整签名 + 公证（notarization）；build.sh 加导出 .dmg 流程；GitHub Releases |

**建议**：v3 按「展示 + 自用」交付，build.sh 预留签名位；确认要做分发了再上公证流程。

### Q5 自启后的产品行为细节（小项，给默认值）

- 开机后**不**自动弹面板，菜单栏安静待命（默认）
- 首次启动**不再**生成演示便签，空白上手（极简方向；反对就说）
- 点其他窗口面板收起并保存的现状行为保留（默认）
