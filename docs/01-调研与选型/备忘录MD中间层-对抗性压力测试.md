# 备忘录「加装 MD 编辑中间层」— 对抗性压力测试与 MVP Patch

> 只读评估，未改动任何代码或系统设置。基于对 `/System/Applications/Notes.app` 的二进制、AppleScript 词典（Resources/Notes.sdef）、快捷指令扩展的实测证据。

## 压力测试结论

你的思路可以成立，但不是以你设想的形式。一句话裁决：**「MD 编辑体验 + 数据继续留在备忘录 + 程序坞不变」可行；「在备忘录窗口内直接敲 MD」不可行，且不值得为它付出任何代价。** 能拿到的是约 85% 的体验，代价是每次编辑多两步固定仪式 + 版本以追加形式累积。前两份评估报告里发现的官方积木（MD 导入/导出、快捷指令）加上新发现的脚本接口，刚好够搭一座单向桥——但把这座单向桥幻想成双向同步，就是熵增的开始。

## 第一性原理拆解

把你的诉求拆成三个不可再分的原子，逐个对照现实：

| 原子需求 | 现实解 | 满足度 |
|---|---|---|
| 编辑体验 = 敲 MD 语法即时渲染的表面 | 备忘录编辑器是 TextKit 富文本内核，无 MD 源码模式；窗口内嵌编辑器物理不可替换 | ❌ 在备忘录内 / ✅ 在平行表面 |
| 资料留存 = 已有数据/附件/iCloud 多端都在 | NoteStore 单一库不动，多端同步继续 | ✅ 完全满足 |
| 不熵增 = 不加 Dock 图标、不加维护面 | 平行表面可以做成菜单栏常驻或 0 安装；但管道本身是新维护面 | ✅ 界面层 / ⚠️ 系统层 |

结论先于细节：**三个原子不可能在同一个表面里同时满足。** 想全都要，只能接受「编辑表面在备忘录外、数据在备忘录内、中间一座单向桥」的折中形态。

## 四条隐含假设逐条拆

**假设 1：备忘录是「可加装插件的宿主」。**
备忘录没有任何插件/扩展架构（连分享和 Spotlight 都是 Apple 自家 appex）。Apple 平台签名 + SIP 意味着任何「装进备忘录里」的方案 = 关闭 SIP + 注入 dylib + patch 签名 → 备忘录启动即失败，每次系统更新重做一遍，且有搞坏 NoteStore 库的真实风险。此路直接判死，不值得做可行性论证。

**假设 2：「不想装 App」≈「不能有第二个进程/表面」。**
约束翻译错了。你真正的约束是**程序坞整洁**（视觉熵），不是进程存在本身。菜单栏常驻 App（无 Dock 图标、全局热键唤出）甚至纯 Shortcuts 流程都满足你的约束。把红线从「不装 App」改划成「不引入需要长期维护的同步管道」，才是有意义的边界。

**假设 3：「不在意留存格式」= 迁移无成本。**
不在意格式只消除了「转换有损」这一项成本（表格 GitHub 语法、脚注、内联 HTML 那些丢损你不在乎，OK）。但 **note 的身份资产是独立成本，而且恰恰是唯一会崩的那个**：它在文件夹里的位置、共享协作链接、附件引用、iPhone 端的阅读体验、Spotlight 索引。实测：AppleScript 词典里 note 的 `container`（所在文件夹）是**只读**，`delete`/`make` 命令**不存在**——脚本既挪不动也删不掉一条 note。「导出 → 编辑 → 导入为新 note」的常规循环，等于每编辑一次就产生一条脱钩旧资产的新 note。

**假设 4：加中间层是熵减。**
中间件管道自身是熵源：macOS 小版本升级会改 Intent 签名和脚本兼容性，iCloud 同步会把脚本误操作放大到所有设备，追加式写回让 note 体积持续膨胀。它把两个系统的故障模式焊在一起，维护成本是持续的；备忘录按原样用，维护成本是 0。熵不会消失，只会转移和放大。

## 三个崩盘点（最可能死在这三处）

### 崩盘点 1：原地写回 = 全场最脆的一环，「可靠写回」与「原地替换」不可兼得

实测证据（Notes.sdef 词典 + IntentsExtension 全集）：

| 能力 | 词典/Intent 现状 |
|---|---|
| 读选中笔记 | ✅ `selection` → `body`(HTML) / `plaintext`，公开可读 |
| 原地改正文 | ⚠️ `body` 词典声明可写，但写的是 **HTML**；带附件的 note 替换 body 后附件引用断裂，现代版本可靠性存疑 |
| 移动/删除 note | ❌ `container` 只读、无 `delete`/`make` 命令 |
| 新建/追加 note | ✅ Shortcuts：`CreateNoteFromMarkdown`、`AppendMarkdownToNote`（已验证存在） |

翻译：**读通路是真的，写通路两条半通。** 可靠的只有「追加」（不原地替换，历史越来越长）；能原地替换的只有 `set body`（写 HTML、附件碎裂风险、可靠性待验证）。你幻想中的「在 MD 里改完，备忘录里同一条 note 原地更新」——每一步都踩在最脆的接口上。

### 崩盘点 2：「在备忘录里敲 MD」在物理上没有合法实现，中间层只能是平行表面 + 桥

备忘录窗口无法寄生 MD 编辑器（无扩展点、签名锁定）。所以中间层 = 另一个窗口（另一个 App 或 Shortcuts 面板）+ 一座桥。而桥的写回端恰好是崩盘点 1。两个崩盘点叠加的结果是：**环形永远闭不干净**——要么追加式（差异累积），要么替换式（附件碎裂风险）。你的原始构想恰好是这两条都不接受的那个交集，不存在。

### 崩盘点 3：Quick Note 双轨制 = 语料库撕裂，iPhone 捕获的笔记永远在 MD 循环之外

你明确要保留 Fn+Q 快速备忘录——它永远走原生富文本编辑器，且 iPhone 端同样只有 create/append。结果是：**(a)** 每条笔记都多一个决策「这条该用哪个表面编」；**(b)** 快速备忘录和 iPhone 随手记的内容，除非手动导出，永远不会流进你的 MD 编辑循环。如果之后想用「iCloud Drive 同步文件夹」自动化补上这条缝，就是 NoteStore vs .md 文件夹双真相源——同步冲突、版本分叉，必崩。这是最容易被忽略、代价最持久的一个。

## MVP Patch（硬边界规则，只给可执行的）

**规则 1 — 单一真相源。** NoteStore 是唯一真相源；.md 文件只是编辑载体，用完即归档到「已处理」文件夹。禁止建立长期双向同步的 .md 文件夹。

**规则 2 — 写回契约按附件分流（核心规则）。**
- 无附件的 note：允许 AppleScript `set body`（MD→HTML→写回）原地替换，**仅在完成证伪清单 b 项验证后启用**；
- 有附件的 note / 一切批量场景：只走「追加 Markdown 到备忘录」，版本累积视为历史留痕；
- 任何第三方工具直写 NoteStore.sqlite：永久禁止（iCloud 同步损坏、无官方恢复）。

**规则 3 — 读取口固定。** 选中 note → AppleScript 读 `body`(HTML) → 本地转 MD → MD 编辑器打开；保存后回调快捷指令写回。全程只用公开接口（`selection` + Shortcuts）。

**规则 4 — Quick Note 保持原生，MD 只用于「重编辑」。** Fn+Q 捕获无所谓格式（你不在意格式）；MD 流水线只处理需要长篇重编的存量笔记，入口仪式固定为「选中 note → 触发」。不给每条笔记留编辑器选择权，消除决策疲劳。

**规则 5 — 零安装第一版。** File → 导出为 Markdown → 任意 MD 编辑器编辑 → 菜单栏快捷指令「追加 Markdown 到备忘录」。安装 App 数 = 0，程序坞不变。只有当「选中→读取→打开」成为稳定的 Top 1 痛点时，才升级为菜单栏常驻热键小工具（不过程序坞，走公开接口，写回仍遵守规则 2）。

**规则 6 — 归档靠改名，删除靠手。** 词典无 `delete`、`container` 只读：脚本删不了也挪不动 note。已重编 note 用 AppleScript 改 `name`（可写）加「🗄」前缀标记版本；移动/删除只能手动，每周一次集中处理。

### 15 分钟证伪清单（先验证再建设，任一不过即走降级路径）

a. 选中一条 note，跑 `osascript -e 'tell application "Notes" to get body of selection'`（首次会弹「允许控制备忘录」授权，点允许），确认返回 HTML；
b. 建一条测试 note，试 AppleScript `set body`：写回是否生效、附件是否保留、iCloud 是否同步；
c. 建一个 Shortcuts：追加 Markdown 到备忘录，验证能否指定目标 note、追加后的样式；
d. File → 导出为 Markdown，检查 .md + 附件文件夹的结构，再「导入 Markdown」验证新 note 落点（iCloud 的「导入的备忘录」文件夹）。

## 最终裁决

1. 「备忘录里直接敲 MD」——**不可行**，为它关 SIP 注入 dylib 是拿库稳定性和每次系统升级换幻觉，不做。
2. 「MD 编辑体验、数据留在备忘录、程序坞不变」——**可行**：平行 MD 表面 + 单向桥（读 body → MD 编辑 → 追加或 set body）。拿到约 85% 体验，成本是每次编辑两步仪式 + 追加式历史。
3. 唯一接近「原地替换」的 `set body` 是全场最脆接口，**只对无附件笔记开放**；带附件的笔记永远走追加式——这不是懒惰，这是附件引用机制的硬约束。
4. 真正的熵减不是把 MD 编辑器塞进备忘录，而是接受「Notes 管存储、MD 管编辑、追加即历史」的单行道设计。试图把单行道修成双向同步，就是熵增本身的开始。
